TLC Meeting - September 10, 2026

Meetings are happening weekly on Thursday at 0700 Pacific / 1000 Eastern / 1500 UK / 1930 India as a video call, and the invite is posted to the #selenium-tlc channel on Selenium Slack. To add items to the agenda for the next meeting, please see our public Rolling Agenda

Participation

  • diemol
  • p0deje
  • titusfortner

Agenda

  • Network async/event API ADR, script and logging async/event API ADR, and low-level WebDriver BiDi layer ADR
  • Selenium Manager released API ADR
  • Element upload method for BiDi file uploads
  • Release automation and Python test duration
  • Selenium Manager cross-compilation and 32-bit Windows
  • Platform-specific Selenium Manager packages
  • Interaction readiness ADR
  • Implementing approved ADRs
  • Contributor PRs outside Selenium 5
  • Java 17 as the minimum version and language version telemetry

Meeting Summary

diemol approved the network ADR again, and titusfortner and diemol agreed to merge the network, script, and low-level BiDi ADRs and revise them later if needed. titusfortner is setting aside the Selenium Manager released API ADR for now, and walked through recent build work: a faster release, cross-compiling Selenium Manager to six binaries, and a fix for Windows architecture detection. p0deje asked how to start implementing the approved ADRs, and diemol proposed raising the Java minimum to 17, which was left open after titusfortner asked for telemetry on Java versions first.

Decisions

  • titusfortner and diemol agreed to merge the network, script and logging, and low-level BiDi ADRs and make any later changes as follow-ups. The network and low-level ADRs merge now, and the script ADR after diemol’s review.
  • The Selenium Manager released API ADR is on hold because it is not a priority right now; diemol agreed. The options planned at the last meeting will not be presented for now.

Discussion Notes

Network, script, and low-level BiDi ADRs

diemol reviewed the changes to the network ADR since the last review, approved it again, and suggested merging. titusfortner proposed merging all three ADRs and handling later changes separately, and will take care of the post-merge housekeeping, such as creating the tracking issue and marking the record published. diemol still wanted to look at one or two of the others. Later in the meeting, titusfortner explained that the low-level ADR ended up describing the same behavior jimevans built in WebDriverBiDi.NET. pujagani and titusfortner reviewed it together, p0deje and AutomatedTester are on board, and implementations exist for Python, Ruby, and Java, so it can merge as well. pujagani’s Java implementation is waiting on review from titusfortner, who will also check on the JavaScript work. That leaves the script and logging ADR for diemol to review and merge.

Selenium Manager released API ADR

titusfortner has struggled to make progress on the record and does not see it as a priority right now, so will come back to it later rather than force it.

Element upload method

AutomatedTester recently raised issues with BiDi file uploads, such as input.setFiles having no file detector for remote browsers. titusfortner proposed a new upload method on element, since BiDi does not send keys to an input and using send keys for uploads no longer makes sense; diemol noted that usage had always been odd. With classic it would delegate to send keys. With Grid it would keep using the file detector approach and the existing Grid file upload endpoint, and otherwise it would go over the BiDi connection. titusfortner wants the method on element rather than on the driver, and sees no need for a special BiDi mechanism for Grid while the existing endpoint works. It may still require subscribing to related events, which titusfortner needs to check. diemol asked whether drag-and-drop uploads could be missed, and titusfortner will look at what BiDi does there. titusfortner was unsure an ADR is needed at this level of detail, but may write a small one that puts upload on element.

titusfortner noted this goes beyond the network and script work into replacing classic behavior with BiDi. Keys and clicks no longer have direct targets in BiDi and go through actions, so those will be built separately. Some of it, as with web extensions, matters before Selenium 5 even if classic commands like click are not replaced yet.

Release automation and Python test duration

titusfortner reported that the Selenium 4.49 release took about an hour and a half from start to finish without problems, and a couple of tweaks could save another half hour. titusfortner plans a PR to merge the pre-release PR automatically when all tests pass, with a Slack message when something fails, in line with other Slack alerts being added. The Python tests take too long. titusfortner streamlined the Ruby tests to remove redundant testing and started the same for Python, but that stalled after limited feedback. diemol was glad the release build works well, suggested leaving it as is to see how the next releases go, and published the release blog post.

Selenium Manager cross-compilation and 32-bit Windows

titusfortner worked through the blockers AutomatedTester had hit with cross-compiling Selenium Manager, so Linux and macOS hosts can now build all six binaries the project wants to release: Windows, macOS, and Linux, each for x64 and ARM64. Building from Windows needs changes to the hermetic LLVM toolchain, which titusfortner has proposed upstream, but that does not block releasing from Linux. Cross-compiling would remove the separate flow the release uses today. titusfortner has not decided whether to leave the PR for AutomatedTester or finish it directly.

Along the way, titusfortner found that Selenium Manager’s Windows architecture detection treated every Windows host as x64. 32-bit Windows users got x64 binaries they could not run, and Windows ARM users got x64 binaries that run under emulation, so 32-bit Windows has effectively been unsupported for about a year and a half. The latest release fixes this. Since cross-compiling only targets x64 and ARM64, titusfortner does not think it matters much if the project stops officially supporting 32-bit Windows, and suggested keeping a 32-bit Windows binary in the Selenium Manager artifacts repository in case someone needs it. That repository would also hold debug binaries and act as an external cache so tests do not rebuild Selenium Manager on every run. titusfortner sees this as simplifying build and release rather than unblocking Selenium 5, and wants to refocus on the network work for Ruby and Python.

Platform-specific Selenium Manager packages

diemol asked about AutomatedTester’s Python issue following up on titusfortner’s proposal. The idea is that the binding package runs on any architecture, and instead of bundling all six Selenium Manager binaries, it pulls in a separate package with only the binary for the user’s platform. diemol questioned whether it is feasible and whether smaller packages justify the work. titusfortner considers it low priority, since the savings are megabytes, and posted it because users have asked and it is the best of several approaches considered. p0deje thought Ruby likely has a way, said Python wheels are doable, and expected Java to be a problem. For Java, the main package would likely depend on every platform package, and users who care could exclude the others in Maven. .NET already handles this through its own ecosystem, so it would apply to npm, gems, and wheels. If users complain once releases include six binaries instead of three, the issue can be pointed to as the solution.

Interaction readiness ADR

titusfortner has not followed up recently on AutomatedTester’s interaction readiness ADR, which uses a single atom to wait for page settledness and element interactability before acting. The two have traded proposals on its structure and the flexibility it gives maintainers and users, and it is not settled yet.

Implementing approved ADRs

p0deje asked whether the plan is to start implementing the approved ADRs. Each approved ADR gets a tracking issue, and titusfortner suggested this meeting start reviewing those tracking issues and the PRs working on them. p0deje wants to start with something small from a tracking issue. titusfortner is more interested in the network work and would rather not dive into script items right now, so those are open for anyone without a preference.

The merged boundaries ADR affects each binding differently. pujagani has done much of the Java work. Ruby needs to remove driver.bidi and fold that functionality into other calls; little was implemented there, so the switch should be easy, though how much deprecation it needs is unclear. Python has BiDi deeply integrated, so it needs a new implementation, and it is unclear whether to deprecate or delete the current API because it is not known how many Python users rely on it. titusfortner will look at both approaches and check whether AutomatedTester’s recent Python work uses the new generated code, which as far as titusfortner knows nothing in Python uses yet. Another option is to make the changes and restore anything users complain about.

The existing ADRs do not cover the transport layer under the low-level BiDi layer, including the message envelope, subscription management, and async handling. titusfortner described three layers: transport, serialization and data objects, and orchestration for handlers. The ADRs define the handler behavior and the low-level layer, and the transport may be an implementation detail that does not need its own ADR. Ruby needs to reimplement subscriptions with the new code; subscription handling currently lives in the WebSocket listener, and titusfortner will look at whether it belongs there or in the BiDi protocol transport class. p0deje asked to hear once that is settled, along with another contributor who may pick up work, and titusfortner wants to bring in more help rather than doing so much alone.

Contributor PRs outside Selenium 5

Some contributor PRs have been waiting for weeks, such as Java logging changes from a motivated contributor, and another contributor has returned with Java cleanup. diemol is taking on PRs not related to Selenium 5, has already handled some of the cleanup, and will review the logging work next, so titusfortner can ignore those and stay on the critical path.

Java 17 minimum and language version telemetry

diemol proposed raising the Java minimum to 17, since many frameworks in the ecosystem, including JUnit, already require it. The plan would be to give vendors a heads-up and make the change in about two months. titusfortner wants data first: the telemetry needs an overhaul, and it should record each language’s version so the project can see how many users of the latest Selenium are still on Java 11. Forcing an upgrade is a harder sell if that is 40% than if it is 5%. titusfortner also noted that many users are still on JUnit 4 and TestNG, that Playwright still supports Java 8, and that the move from 8 to 11 was driven by the JDK HTTP client, and asked what Selenium would gain beyond features like records. diemol said it is mostly housekeeping for now, but better done before it becomes urgent. No decision was made. diemol will review the open PR that reports language version to telemetry so titusfortner can stay focused on Selenium 5.

Action Items

  • titusfortner will merge the network and low-level BiDi ADRs and handle the follow-up housekeeping.
  • diemol will review the script and logging ADR and merge it once satisfied.
  • titusfortner will look at what BiDi file uploads require and may write a short ADR for an element upload method.
  • titusfortner will open a PR to merge the pre-release PR automatically when tests pass, with a Slack alert on failure.
  • titusfortner will tidy up the Selenium Manager cross-compilation work and may write up a plan for the six binaries and the artifacts repository.
  • titusfortner will review and merge pujagani’s Java BiDi implementation.
  • titusfortner will look at where Ruby BiDi subscription handling belongs and let p0deje know.
  • p0deje plans to look at the ADR tracking issues for a small task to pick up.
  • titusfortner will look at AutomatedTester’s Python BiDi work and the options for deprecating or removing the current Python BiDi API.
  • diemol will handle contributor PRs not related to Selenium 5, starting with the Java logging changes.
  • diemol will review the language version telemetry PR.

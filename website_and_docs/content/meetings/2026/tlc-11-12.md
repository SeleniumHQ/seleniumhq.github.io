## Meeting Summary

[titusfortner] reviewed where the outstanding ADRs stand against Selenium 5 and asked to settle the
[Selenium 5 scope PR][selenium-18293] before a separate conversation about the roadmap after it.
Much of the meeting covered how event subscriptions are scoped: [titusfortner] backed
[AutomatedTester]'s [change to the network ADR][selenium-18279] so unscoped handlers apply to every
window, and both agreed that high-level APIs scope by window handle. The group also covered the
options in the [alert handling ADR][selenium-18283], Classic support for [accessibility
snapshots][selenium-18205], and two PRs on ADR authoring guidance. After [AutomatedTester] and
[diemol] left, [titusfortner] and [jimevans] compared the proposed low-level subscription behavior
with how WebDriverBiDi.NET handles events.

## Decisions

* [titusfortner] proposed discussing the roadmap beyond Selenium 5, as described in the [scope
  PR][selenium-18293] body, separately from that PR, and [AutomatedTester] agreed and was happy to
  defer it. The scope PR itself still needs agreement.
* Handlers registered without a scope default to global, covering every window. [titusfortner]
  agreed with [AutomatedTester]'s [network ADR replacement][selenium-18279] on this and said it
  should be approved, and [AutomatedTester] accepted global as a default to try and revisit if
  needed. This reverses the network ADR's earlier default of the window current at registration,
  which the [September 3 minutes][tlc-09-03] recorded as settled. The replacement record was not
  formally accepted in the meeting.
* High-level APIs scope by window handle, the equivalent of a tab or top-level navigable, so they
  do not need to refer to browsing contexts. [AutomatedTester] and [titusfortner] agreed on this.
* [AutomatedTester] and [titusfortner] agreed that [accessibility snapshots][selenium-18205] can
  also support Classic sessions by running the atom through execute script, and that a pinned
  script can be added later without breaking that. [diemol] supported covering Classic as well.

## Discussion Notes

### Selenium 5 ADR status and scope

[diemol] noted the agenda was meant to show which ADRs still need review and how far the accepted
ones have been implemented. [titusfortner] had gone through all outstanding ADRs and found several
outdated: they depend on proposals that have since closed, or were submitted before the Selenium 5
boundaries were decided. In [titusfortner]'s view, only the low-level BiDi layer and some web
extension work are implemented so far. Network is the only accepted high-level API, and nobody has
implemented it because Python and Ruby must deprecate their existing BiDi code to move to the
CDDL-generated layer, and those deprecations do not work while low-level users cannot reach events
the way they can reach commands. Some of [AutomatedTester]'s recent PRs aim to fill that gap with
new high-level APIs. [titusfortner]'s alternative is the [low-level subscriptions
ADR][selenium-18299]: give users commands and subscriptions at the low level, deprecate the current
public classes, and build the new high-level APIs gradually. On that basis, [titusfortner] argued a
browsing context ADR is not needed before Selenium 5.

[titusfortner] used the [scope PR][selenium-18293] body to describe the expected direction of
implementation after Selenium 5, because [AutomatedTester] pictures that differently and the
difference keeps resurfacing in individual PRs. For example, [titusfortner] likes parts of the
[windows proposal][selenium-17681] but thinks some of it is not needed, and believes both agree on
what the main high-level ADRs for Selenium 5 need. [AutomatedTester] was happy with the plan, happy
to defer the rest, and not attached to any particular proposal, coming from the perspective that
BiDi is shaped very differently from Classic: some concepts should be carried over, while others do
not fit. [titusfortner] suggested scheduling the roadmap conversation separately, possibly offline
with [AutomatedTester], and wants [jimevans]'s input as well.

### Subscription scoping and the network default

[AutomatedTester] said the terms were being used loosely in the record: a browsing context can be
more than a tab or frame, extending into realms.
[titusfortner] explained that the remote end translates any subscribed browsing context to its
top-level navigable and emits events for that whole tree, which can be called the page.
[AutomatedTester] suggested the group treat a top-level navigable as a tab, since Classic users
generally work in one tab at a time, which simplifies the rest of the model.

Users of the internal layer can pass any browsing context, so the open question was whether the
low level should mirror the remote end or add behavior before sending a subscription.
[AutomatedTester] answered both, noting that in the Classic model, user context and browsing context
mean much the same thing, so subscriptions can be made globally and the client left to pick what it
wants, which is fine for Selenium 5. [AutomatedTester] asked that whatever is chosen be as
extensible as possible, and [titusfortner] agreed. On the network ADR, [titusfortner] said limiting
the default to the current window was not right because it should follow the remote end, which
applies to everything unless given a scope.

[titusfortner]'s principle is that no layer should process events it does not need, so filtering
happens at every level that can filter. For network, the public class will register one listener on
the socket and filter among the user's handlers, while the low level also filters by what it was
sent.
Both layers need a browsing context tree. [titusfortner] now thinks the low level must subscribe to
`browsingContext.contextCreated` to keep its tree in sync and will change the [Python
implementation][selenium-18300] accordingly. [AutomatedTester] agreed and stressed that this means
tracking and understanding browsing contexts. [titusfortner] still holds that the record does not
need to define anything at the window level and covers what Selenium 5 needs about browsing and user
contexts, and asked for more feedback. [AutomatedTester] is also updating a [Python network
PR][selenium-18051]. [titusfortner] has not reviewed it yet and plans to try a Ruby implementation
first to catch missing use cases so the two match.

### Alert handling ADR options

[titusfortner] asked for a choice among the three options in the [alert handling
ADR][selenium-18283] PR body before the record itself is reviewed, and is holding the Ruby
implementation until then. Option 1 is async-only, as in WebdriverIO. Option 2 keeps synchronous
alert handling but drops the "unhandled" prompt behavior, so code errors when an alert is not
handled explicitly. Option 3, which the record currently proposes, keeps the "unhandled" behavior
and is fully backward compatible. [AutomatedTester] voted for Option 2, as numbered in the PR body.
[titusfortner] said Option 3 is doable, with a few race conditions that the specification PR
[webdriver-bidi#1185] would address, and floated choosing Option 3 if that merges
and Option 2 if it does not. The implementation effort differs little between the two; Option 2 may
be easier to explain but could require users to change their code. [diemol] had not yet given an
opinion on the options.

### Accessibility tree snapshots

[AutomatedTester] had replied to the review comments on the [accessibility ADR][selenium-18205],
which currently leaves Classic sessions out. [titusfortner] asked whether Classic should be
supported and whether a snapshot should be scoped to the current frame rather than the page.
[AutomatedTester] had not been considering Classic, but said the atom could run through execute
script, as getAttribute does, which would give Classic users weighing a move to Playwright for
accessibility features a reason to stay. The atom is large, and an earlier version used a preload
script that [AutomatedTester] would like to return to; [titusfortner] said pinned scripts could be
added later while staying compatible. Scoping to the current frame is doable by working from the
current document. [diemol] was satisfied after the final comments, had assumed the record covered
both Classic and BiDi, and said it would be good to have it so the code can be released and refined,
especially for .NET. [titusfortner] wants the Java, Ruby and .NET implementations
[removed][selenium-18291] until the group can walk through them, keeping Python and JavaScript for
the release.

### ADR authoring guidance

[titusfortner] and [AutomatedTester] each opened a PR to improve the ADR documentation and
requirements: [#18303][selenium-18303] and [#18306][selenium-18306]. [AutomatedTester] had read a
review comment on the accessibility ADR as a request to do this. [titusfortner]'s PR adds an
`AGENTS.md` for decision records, because an agent given a template fills in every section whether
or not it is needed; one ADR nearly doubled in size during review from additions that were not
needed to address the feedback. [AutomatedTester] added that agents do not read contribution
guides unless told to explicitly. [titusfortner] points agents to the README, which lists the
documents to follow, but was not sure that includes the contributing guide. [titusfortner] finds
agents necessary for the volume of information but is wary of their effect on readability for
people.

### Low-level event handling in WebDriverBiDi.NET

After [AutomatedTester] and [diemol] left, [titusfortner] asked [jimevans] for feedback on the
[low-level subscriptions ADR][selenium-18299], which [jimevans] had not yet read. [titusfortner] had
noticed that [Dramaturge][dramaturge], the higher-level library [jimevans] built on
[WebDriverBiDi.NET][webdriverbidi-net], offers both parallel and sequential handler execution. The
main place parallel execution would help is network interception, but Selenium's network handlers
run as a last-in, first-out chain, so it does not help there.

[jimevans] explained that in WebDriverBiDi.NET each handler is registered to run synchronously or
asynchronously. Incoming events are dispatched to listeners in order, and whether dispatch waits for
a handler depends on that setting. A handler that sends a command over the wire, which is common in
network handling, must run asynchronously so it does not block the reader, and [jimevans] built a
custom event observer to support this. [titusfortner] confirmed the last-in, first-out ordering
belongs to the high level, which keeps an ordered list and runs it inside its single listener, and
[jimevans] agreed that sounds right. [titusfortner] expects the high level to wrap each user
callable so it receives the object Selenium wants it to use, and thinks the low level should
validate the payload that object is built from.

[titusfortner] said it would be convenient if BiDi included subscription IDs with events, as it
does intercept IDs for blocked network requests, though that may be a burden for the remote end.
[jimevans] sees it as a potential security hole: if two sessions are connected to the same browser,
for example one monitoring network traffic and one driving, and both subscribe to
`browsingContext.load`, each would receive an ID belonging to the other. [jimevans] raised this with
the working group when the .NET maintainer proposed something similar ([webdriver-bidi#1032]). Every
event already carries its browsing context and may carry its user context, which [jimevans] expects
to become mandatory; that is enough to tie an event back to what a session tracks.

The WebDriverBiDi.NET low-level layer is a protocol wrapper that surfaces every subscribed event and
does no routing. That is left to the higher level, and [jimevans] believes that in Dramaturge each
page or frame has its own handler that filters out events from other contexts. [titusfortner] is
proposing instead that Selenium's low level never delivers an event to a listener whose requested
scope does not match, using a map from each context to its top-level context built from
`browsingContext.contextCreated`. After checking the code, [jimevans] corrected an earlier
recollection that handlers take a filter predicate: WebDriverBiDi.NET has two observer types, a
push model that runs a handler for each event and a pull model whose event collector gathers
events, applying a filter as it collects, for the caller to inspect on demand. [jimevans] likes
having both.

[titusfortner] reported on raising Selenium's prompt handling problems at TPAC and outlined three
options that the upcoming prompt ADR will present, with a capabilities ADR to follow. Selenium 4.52
was released the morning of the meeting, and a few release fixes are ready to push. Much of the
discussion covered how the TLC keeps up with PR review load and makes sure items that need
consensus get decided. [harsha509] will propose an ADR for migrating the JavaScript bindings to

## Discussion Notes

### Prompt handling after TPAC

[titusfortner] joined the TPAC session by video to discuss prompt handling. Attendees had not had
time to read the material in advance; they generally agreed with [titusfortner]'s analysis but did
not commit to anything. Some of the discussion should still help with how Selenium manages backwards
compatibility.

This work started with capabilities: with BiDi, the bindings have to manage timeouts, strict file
interactability, and unhandled prompt behavior locally. Prompts looked like a simpler place than
network to define how subscriptions work in the bindings, by subscribing to the event with a
default handler that users can override. It turned into a question of backwards compatibility and
of browsers behaving differently in different places. [titusfortner] laid out three options:

1. Follow WebdriverIO, which stopped supporting synchronous prompt handling in version 9. Users
   register their own async handler, and backwards compatibility is dropped. WebdriverIO users
   have since opened issues and PRs asking for more, and [titusfortner] explained on one of them
   why it would need larger changes to WebdriverIO.
2. A hybrid that keeps the synchronous Alert API, implemented over BiDi with a prompt store, but
   removes unhandled prompt behavior. Users either configure prompts to be accepted or dismissed as
   soon as they open, or handle them in code; a prompt that is open when another command is sent
   is no longer dismissed automatically.
3. Be fully backwards compatible on the client side. The bindings would track open prompts per
   browsing context so users can synchronously wait for and query them. A BiDi script command that
   opens a prompt hangs, where classic returns as soon as the prompt opens, so the bindings would
   also track pending commands per browsing context and cancel or time out the pending command
   when a prompt opens. Some race conditions would remain unless remote ends change.
   [titusfortner] has opened specification PRs on prompt behavior ([webdriver-bidi#1184],
   [webdriver-bidi#1185]); browser changes from one of them would help, but are not required to be
   mostly compatible.

[titusfortner] is not sure the hybrid is different enough to implement from full compatibility to
justify giving up backwards compatibility. The prompt behavior ADR is drafted, a capabilities ADR
based on it comes next, and other ADRs will follow later.

### Selenium 4.52 release

The release ran end to end in 33 minutes, though [titusfortner] found it skipped waiting on a step
it should have waited on, which would bring it to about 40 minutes; skipping it did not cause
problems this time. The .NET publish step failed verification because the workflow did not allow
enough time for package validation before publishing. [titusfortner] plans to make that
verification asynchronous so it warns later instead of blocking the release, and also started
cleaning up Python deprecations, including items deprecated three years ago that were never removed
and one that was not deprecated correctly, but held that work so the release could go out.
[titusfortner] expects the next release to be easier.

### Script and logging async/event API ADR

[titusfortner] reminded [diemol] about reviewing the [script and logging ADR][selenium-17776],
which [diemol] had wanted to do before approving it, and believed the rest of the TLC had already
approved it. It is the only other major outstanding ADR item, and [diemol] acknowledged the request.

### JavaScript to TypeScript migration

[diemol] asked [harsha509] about the TypeScript work. Despite being busy with Appium work,
[harsha509] will write an ADR, as [diemol] suggested earlier, on how to replace JavaScript with
TypeScript gradually. The code already exists, and [harsha509] has been testing it and keeping it
rebased. Because Nightwatch uses the JavaScript bindings as a dependency, [harsha509] wants to
discuss the rollout with the BrowserStack team and with [pujagani] and [AutomatedTester];
[pujagani] noted that [AutomatedTester] knows Nightwatch better.

### Selenium IDE maintenance

[harsha509] offered to help with Selenium IDE, understanding it to be all TypeScript. [diemol] is
not developing new features, but is updating dependencies and checking open issues that block a
new release, since people are still using it, and is considering publishing the extension with
Manifest V3. The goal is to get a release out and leave it there.

### Appium compatibility

[harsha509] said Appium's next release is in beta and could come as soon as next week, and asked
whether Selenium needs to do anything for compatibility. [diemol] did not think so: Appium's Java
bindings used to have many dependencies on Selenium's Java bindings, and those appear to have been
removed. [diemol] was not sure about the other languages.

### PR review load and bringing decisions to the TLC

[pujagani] has nothing waiting on [titusfortner]'s review yet, having mostly added tests since the
[Java generator][selenium-17777] landed. [titusfortner] wants to file issues for problems found
instead of fixing each one personally, and contributors have already opened PRs for some of them,
which [pujagani] reviews or builds on. [diemol] is working through the outstanding Grid PRs and
reported rejecting one that went against the Grid's original design, which is not written down
anywhere.

[diemol] raised that there are more PRs than the TLC can review, in both the documentation and the
main repository, and asked whether a TLC member's PR should go ahead when the idea is agreed and a
review agent finds no problems. [titusfortner] thinks some
open PRs need to be closed or reworked. For example, a Python network handler implementation was
built on the older code rather than the new internal BiDi layer. Some documentation PRs may rest on
assumptions the TLC has since decided against, though [titusfortner] was not certain, and some PRs
mix larger decisions, such as whether to add syntactic sugar methods for expectations, with other
changes. Those questions tend to be tabled and not revisited.

[titusfortner] already self-merges work when it is not contentious and holds it for review when it
might need discussion. With no opinions yet on what the Selenium Manager based CLI should support,
[titusfortner] is content to let [AutomatedTester] decide, and did not think any recently landed
work skipped discussion, at least in principle. [diemol] saw no harm in publishing the atoms and
Selenium Manager as npm packages. In [titusfortner]'s view, the missing piece is consistent TLC
meetings where items that need consensus go on the agenda, which depends on consistent attendance.
[titusfortner] noted that some recent minutes have not been published yet.

### AI-assisted contribution policy

[harsha509] asked whether the project has a policy for AI-generated PRs. [diemol] pointed to the PR
template section added by the [AI-assisted contribution policy][selenium-17043], where contributors
say whether and how they used AI and confirm they can explain the change. [diemol] rejects PRs that
do not use the template. Asked about contribution guidelines, [diemol] said the project still
expects small, easily reviewable PRs, and suggested rejecting PRs that do not meet those basics,
noting that PRs with no associated issue are also coming in, apparently from agents scanning the
repository for bugs without the context for why the code is written as it is. [harsha509] and
[diemol] both supported changing the minimum number of PRs expected for the committer role.
[harsha509] said Appium is starting to work on a similar template.

[diemol] reported that TestMu AI has approval to proceed with a Selenium conference in India.

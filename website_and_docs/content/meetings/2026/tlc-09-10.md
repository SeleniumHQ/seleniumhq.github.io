### Element upload method

[AutomatedTester] recently raised issues with BiDi file uploads, such as [`input.setFiles` having no
file detector for remote browsers][selenium-18008]. [titusfortner] proposed a new `upload` method
on element, since BiDi does not send keys to an input and using send keys for uploads no longer
makes sense; [diemol] noted that usage had always been odd. With classic it would delegate to send
keys. With Grid it would keep using the file detector approach and the existing Grid file upload
endpoint, and otherwise it would go over the BiDi connection. [titusfortner] wants the method on
element rather than on the driver, and sees no need for a special BiDi mechanism for Grid while the
existing endpoint works. It may still require subscribing to related events, which
[titusfortner] needs to check. [diemol] asked whether drag-and-drop uploads could be missed, and
[titusfortner] will look at what BiDi does there. [titusfortner] was unsure an ADR is needed at
this level of detail, but may write a small one that puts `upload` on element.

[titusfortner] noted this goes beyond the network and script work into replacing classic behavior
with BiDi. Keys and clicks no longer have direct targets in BiDi and go through actions, so those
will be built separately. Some of it, as with web extensions, matters before Selenium 5 even if
classic commands like click are not replaced yet.

### Release automation and Python test duration

[titusfortner] reported that the Selenium 4.49 release took about an hour and a half from start to
finish without problems, and a couple of tweaks could save another half hour. [titusfortner] plans
a PR to merge the pre-release PR automatically when all tests pass, with a Slack message when
something fails, in line with other Slack alerts being added. The Python tests take too long.
[titusfortner] streamlined the Ruby tests to remove redundant testing and started the same for
Python, but that stalled after limited feedback. [diemol] was glad the release build works well,
suggested leaving it as is to see how the next releases go, and published the release blog post.

### Selenium Manager cross-compilation and 32-bit Windows

[titusfortner] worked through the blockers [AutomatedTester] had hit with [cross-compiling Selenium
Manager][selenium-17586], so Linux and macOS hosts can now build all six binaries the project wants
to release: Windows, macOS, and Linux, each for x64 and ARM64. Building from Windows needs changes
to the hermetic LLVM toolchain, which [titusfortner] has proposed upstream, but that does not block
releasing from Linux. Cross-compiling would remove the separate flow the release uses today.
[titusfortner] has not decided whether to leave the PR for [AutomatedTester] or finish it directly.

Along the way, [titusfortner] found that Selenium Manager's [Windows architecture
detection][selenium-17987] treated every Windows host as x64. 32-bit Windows users got x64 binaries
they could not run, and Windows ARM users got x64 binaries that run under emulation, so 32-bit
Windows has effectively been unsupported for about a year and a half. The latest release fixes
this. Since cross-compiling only targets x64 and ARM64, [titusfortner] does not think it matters
much if the project stops officially supporting 32-bit Windows, and suggested keeping a 32-bit
Windows binary in the Selenium Manager artifacts repository in case someone needs it. That
repository would also hold debug binaries and act as an external cache so tests do not rebuild
Selenium Manager on every run. [titusfortner] sees this as simplifying build and release rather
than unblocking Selenium 5, and wants to refocus on the network work for Ruby and Python.

### Platform-specific Selenium Manager packages

[diemol] asked about [AutomatedTester]'s [Python issue][selenium-18001] following up on
[titusfortner]'s [proposal][selenium-17943]. The idea is that the binding package runs on any
architecture, and instead of bundling all six Selenium Manager binaries, it pulls in a separate
package with only the binary for the user's platform. [diemol] questioned whether it is feasible
and whether smaller packages justify the work. [titusfortner] considers it low priority, since the
savings are megabytes, and posted it because users have asked and it is the best of several
approaches considered. [p0deje] thought Ruby likely has a way, said Python wheels are doable, and
expected Java to be a problem. For Java, the main package would likely depend on every platform
package, and users who care could exclude the others in Maven. .NET already handles this through
its own ecosystem, so it would apply to npm, gems, and wheels. If users complain once releases
include six binaries instead of three, the issue can be pointed to as the solution.

### Interaction readiness ADR

[titusfortner] has not followed up recently on [AutomatedTester]'s [interaction readiness
ADR][selenium-17886], which uses a single atom to wait for page settledness and element
interactability before acting. The two have traded proposals on its structure and the flexibility
it gives maintainers and users, and it is not settled yet.

### Implementing approved ADRs

[p0deje] asked whether the plan is to start implementing the approved ADRs. Each approved ADR gets
a tracking issue, and [titusfortner] suggested this meeting start reviewing those tracking issues
and the PRs working on them. [p0deje] wants to start with something small from a tracking issue.
[titusfortner] is more interested in the network work and would rather not dive into script items
right now, so those are open for anyone without a preference.

The merged [boundaries ADR][selenium-17670] affects each binding differently. [pujagani] has done
much of the Java work. Ruby needs to remove `driver.bidi` and fold that functionality into other
calls; little was implemented there, so the switch should be easy, though how much deprecation it
needs is unclear.
Python has BiDi deeply integrated, so it needs a new implementation, and it is unclear whether to
deprecate or delete the current API because it is not known how many Python users rely on it.
[titusfortner] will look at both approaches and check whether [AutomatedTester]'s recent Python
work uses the new generated code, which as far as [titusfortner] knows nothing in Python uses yet.
Another option is to make the changes and restore anything users complain about.

The existing ADRs do not cover the transport layer under the low-level BiDi layer, including the
message envelope, subscription management, and async handling. [titusfortner] described three
layers: transport, serialization and data objects, and orchestration for handlers. The ADRs define
the handler behavior and the low-level layer, and the transport may be an implementation detail
that does not need its own ADR. Ruby needs to reimplement subscriptions with the new code;
subscription handling currently lives in the WebSocket listener, and [titusfortner] will look at
whether it belongs there or in the BiDi protocol transport class. [p0deje] asked to hear once that
is settled, along with another contributor who may pick up work, and [titusfortner] wants to bring
in more help rather than doing so much alone.

### Contributor PRs outside Selenium 5

Some contributor PRs have been waiting for weeks, such as Java logging changes from a motivated
contributor, and another contributor has returned with Java cleanup. [diemol] is taking on PRs not
related to Selenium 5, has already handled some of the cleanup, and will review the logging work
next, so [titusfortner] can ignore those and stay on the critical path.

### Java 17 minimum and language version telemetry

[diemol] proposed raising the [Java minimum to 17][selenium-16732], since many frameworks in the
ecosystem, including JUnit, already require it. The plan would be to give vendors a heads-up and
make the change in about two months. [titusfortner] wants data first: the telemetry needs an
overhaul, and it should record each language's version so the project can see how many users of
the latest Selenium are still on Java 11. Forcing an upgrade is a harder sell if that is 40% than
if it is 5%. [titusfortner] also noted that many users are still on JUnit 4 and TestNG, that
Playwright still supports Java 8, and that the move from 8 to 11 was driven by the JDK HTTP client,
and asked what Selenium would gain beyond features like records. [diemol] said it is mostly
housekeeping for now, but better done before it becomes urgent. No decision was made. [diemol] will
review the open [PR that reports language version to telemetry][selenium-16733] so [titusfortner]
can stay focused on Selenium 5.

## Meeting Summary

[AutomatedTester] gave an update on upstreaming the atoms into Appium, which led into whether
`innerText` can replace the visible text atom and then into dropping Internet Explorer support in
Selenium 5, which [titusfortner], [AutomatedTester], and [jimevans] agreed to in principle pending
usage data. [titusfortner] gave updates on the unhandled prompt behavior ADR, a Chrome navigation
issue holding up the release, and Snap support in Selenium Manager. The group also went through
PRs awaiting review and discussed promoting the WebdriverIO v10 release and setting up Qodo
accounts for active contributors.

## Decisions

* [titusfortner], [AutomatedTester], and [jimevans] agreed in principle to drop Internet Explorer
  support in Selenium 5, with users who need IE staying on Selenium 4. This is pending IE mode
  usage data that [AutomatedTester] will request from a contact on the Microsoft Edge team.
* [titusfortner] was okay with [AutomatedTester]'s proposal to promote the WebdriverIO v10 release
  on the Selenium blog or socials.
* [AutomatedTester] agreed with [titusfortner]'s plan to give active contributors seleniumhq.org
  email aliases so they can get Qodo accounts and automated AI review of their PRs.

## Discussion Notes

### Atoms and visible text

[AutomatedTester] is upstreaming the atoms npm package into Appium. An Appium maintainer said
three atoms would cover most of what Appium needs, though it was unclear how much of the rest is
used, so [AutomatedTester] is checking the list. [AutomatedTester] found the list in the [atoms
TypeScript rewrite issue][selenium-15596] largely correct, and [titusfortner] asked for it to be
updated as items are addressed. The open question is how much each consumer actually uses:
Chromium still carries many atoms for historical reasons, while Firefox uses only two, for
displayedness and visible text, and embeds the full compiled function inline. [titusfortner] asked
whether Firefox could import them from the npm package instead; [AutomatedTester] said possibly,
but did not think Firefox needs that now.

[AutomatedTester] suggested Firefox may be able to drop the visible text atom, since `innerText`
now returns roughly what a user would get by highlighting the page and leaves out hidden text.
[titusfortner] recalled [jimevans] suggesting that the BiDi implementations, which will have to
handle this on the client side, might use `innerText` instead of the atom. After joining,
[jimevans] clarified that this was an untested hypothesis. The atom exists to walk the DOM and
account for styling and visibility, which makes it complex and probably one of the slowest things
the atoms do. `innerText`, which [jimevans] believes has since been standardized, is meant to omit
invisible text, unlike `textContent`. [AutomatedTester] recalled that the atom was kept mainly
because differences between IE and Edge could not be verified or debugged, not because of
differences between Chrome and Firefox.

### Dropping Internet Explorer support in Selenium 5

With IE mode in Edge used less and less, [AutomatedTester] and [jimevans] did not think those
differences matter much anymore. [titusfortner] asked whether the project could drop IE support in
Selenium 5 and tell users who need IE to keep using Selenium 4, and both were okay with that.
[jimevans] said the long-term plan worked out with Microsoft was best-effort support through about
2029, but usage now appears negligible even for internal applications, and if support is going to
end officially, Selenium 5 is the right time. [titusfortner] noted the project last updated the IE
driver code, in minor ways, about two and a half to three years ago, and Microsoft has made only a
couple of security fixes. If a security issue does come up, a special Selenium 4 release remains
possible. [titusfortner] also raised that the project could report the IE mode capability to
Plausible to measure usage.

[AutomatedTester] would treat the lack of IE issues as a yardstick and will ask a contact on the
Microsoft Edge team for data on how many people use IE mode. Selenium users would be a small
fraction of that number, so if it is low, continued support is not worth the project's time.
[jimevans] recommended moving the IE driver code into its own repository when it is removed, so it
stays available without restoring an earlier commit, since that part of the tree is fairly
isolated. [AutomatedTester] was fine with that. [Issue #17546][selenium-17546] tracks removing the
IE driver code.

### Unhandled prompt behavior ADR

[titusfortner] is stuck on the ADR for unhandled prompt behavior because the BiDi behavior is not
backwards compatible: with BiDi enabled, existing alert tests fail because BiDi has no `dismiss and
notify` option. [titusfortner] thinks the approach [jimevans] proposed the previous week works but
has not fully verified it. [titusfortner] also wants to raise a W3C issue, since what the BiDi
capability controls is not really unhandled prompt behavior, it applies in a different place, and
it accepts many parameters the classic capability does not. Because the behavior is genuinely
different, Selenium will need to handle backwards compatibility between the two, which
[titusfortner] thinks is doable, but a new name would be clearer than treating one capability as
working for both.

### PR review status

[titusfortner] congratulated [pujagani] on merging the [Java BiDi generator][selenium-17777].
Reviewing it took a while because agents flag many small issues of unclear importance, and
[pujagani] noted strict typing makes that trickier. [titusfortner] also pointed [pujagani] to a
contributor PR fixing a JSON traversal performance problem, where one scenario makes an excessive
number of calls; it affects BiDi generation, which relies heavily on the JSON handling.

[AutomatedTester] asked what is needed to land the [Python web extensions PR][selenium-17970] and
asked for opinions on [#18051][selenium-18051], which builds the Python `driver.network` on the
internal BiDi layer per the network ADR, and [#18052][selenium-18052], which adds unit tests for
the Python BiDi protocol generator under the low-level BiDi ADR, tracked in
[#18020][selenium-18020]. [pujagani] added the [JavaScript web extensions PR][selenium-18127].
[titusfortner] will review all four, using an agentic review as another set of eyes;
[AutomatedTester] noted that because LLMs are non-deterministic, multiple agent reviews turn up
different findings. The [Java web extensions PR][selenium-18036] was waiting on the generator, and
[pujagani] will land a few generator changes for vendor extensions before reworking it.

[titusfortner] reported that the Mozilla CDDL files are now pulled in and generated from
dynamically rather than kept as local copies, though some of it may still be hard-coded.
[titusfortner] also said one of the priorities needs to be moving off the old Python generator,
which is running into bugs. Separately, a Bluetooth message that was renamed a couple of times
caused issues in both generators.

Many contributor issues and PRs outside the BiDi work are still waiting for review, including a set
of Java logging PRs that has been open for about two months and that [titusfortner] gave feedback
on and thinks was ready afterward. [titusfortner] said it is frustrating not to work with
contributors who are trying to help, and the project needs more bandwidth for it.

### Chrome navigation issue and Snap support in Selenium Manager

A new Chrome version is out, and the release was ready except for a bug where navigating too soon
after starting Chrome fails. [titusfortner] first thought it only affected BiDi but reproduced it
in classic as well. [titusfortner] at first proposed a one-second sleep after starting Chrome to
fix the remaining failing test, but later in the meeting traced the likely cause to Selenium
Manager skipping a sandbox-related setup step when installing Chrome for Testing; without it,
navigations misbehave. The fix is in Rust, and the release will follow once it is verified.

[titusfortner] also thinks Selenium Manager can now support Snap and has a PR nearly ready, pending
a check that the Rust approach is right. A Selenium fix removed a side effect Rails relied on, and
the follow-up fix in Rails broke a Snap setup that had only worked by accident under the old code.
Selenium Manager has the information needed to handle this properly.

### WebdriverIO v10 release

[AutomatedTester] noted that WebdriverIO shipped its v10 release and proposed supporting the
project where possible, such as with a post on the Selenium blog or socials, as a way of supporting
the community. [AutomatedTester] was unsure whether this falls to the TLC or another project group.

### Qodo accounts for active contributors

Qodo's automated PR review now requires each contributor to have a Qodo account, and accounts need
a seleniumhq.org email address. The project has an enterprise account, so the limit is permissions
rather than capacity. [titusfortner] proposed seleniumhq.org aliases that forward to contributors'
own addresses for anyone who actively submits PRs, so their PRs are reviewed automatically.
[titusfortner] invited [AutomatedTester], [p0deje], and [jimevans] during the meeting.

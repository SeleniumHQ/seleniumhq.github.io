## Meeting Summary

[titusfortner] presented three changes expected to be uncontroversial: the [charter's
out-of-scope list][selenium-18293], the [network ADR replacement][selenium-18279], and new [ADR
authoring guidance][selenium-18303]. [AutomatedTester] raised how the CLI and MCP work relates to

run sequentially or concurrently, which was left for further review.

## Discussion Notes

### Selenium 5 charter

The [charter PR][selenium-18293] lays out where [titusfortner] expects BiDi features to land in the
existing Selenium API after Selenium 5. It was written because [titusfortner] and [AutomatedTester]
have had competing ideas about what comes after Selenium 5 and are approaching the Selenium 5 work
with different end goals. The only change to the charter itself is stating explicitly what is out of
scope. The longer-term roadmap still needs its own discussion later.

### Network handler ADR replacement

The ADR process requires an accepted record to be marked superseded and linked to its replacement,
so there is a single source of truth. The [original network ADR][selenium-17685] scoped unscoped
handlers to the current window, which [titusfortner], its author, said was wrong.
[AutomatedTester]'s [replacement][selenium-18279] changes the default so handlers apply to every
window unless narrowed. [titusfortner] asked for explicit approving reviews so it can merge.

### ADR authoring guidance

[titusfortner] wrote the [guidance][selenium-18303] after repeatedly correcting AI agents that treat
every template section as something to fill in, which leads to duplication; one record doubled in
size while addressing review feedback. The guidance limits a record to what is needed to implement
the decision, moves less durable material to the PR body, and asks that records be written so a
later ADR can extend one instead of rewriting it. It adds a separate agents file for agents working
on records. It also states that a binding may add optional behavior without a record as long as the
names, behavior, and defaults an ADR defines are kept, such as Ruby adding an observe-only network
mode, with the understanding that a later ADR may change it. Implementation PRs stay in draft until
their record is accepted, as do proposals that depend on outside work landing first.

### CLI, MCP, and Selenium Manager

[AutomatedTester] asked whether the official release of the CLI and MCP work should wait for
Selenium 5, noting it is technically already released through the `@selenium/manager` npm package.
[AutomatedTester] wants it to stay part of Selenium Manager, without needing a rename: the CLI side
is largely done and the MCP work is nearly ready, some people already use it, it benefits from being
written in Rust, and it builds on the browser setup work [bonigarcia] did in Selenium Manager, so
the agentic features are small additions. [titusfortner]'s view is that a binary Selenium releases
that now does several things needs to be defined as part of Selenium 5, possibly with a new name,
and that the Selenium Manager released API ADR should account for the CLI. The CLI is still in beta,
and some of the API changes [titusfortner] is proposing are meant to keep it backward compatible
going forward.

[AutomatedTester] confirmed the CLI sits in a separate area of the codebase from driver management,
and on that basis [diemol] does not want it added to the Selenium 5 charter. [diemol] agreed an ADR
is needed and supports defining Selenium Manager's move out of beta, but sees no reason to wait for
Selenium 5 to release the CLI. [titusfortner] noted the CLI runs from the same binary, which raises
naming and versioning questions for a stable Selenium Manager release, but agreed nothing should be
added that slows Selenium 5; [AutomatedTester] said that is not being proposed, and expects the CLI
work not to affect Selenium 5 timelines since [AutomatedTester]'s time will go to other Selenium 5
work.

Separately, [titusfortner] had proposed that releasing Selenium Manager independently of Selenium
requires both forward and backward compatibility. [diemol] had questioned why backward compatibility
alone is not enough, and [titusfortner] sees a middle ground that still needs to be written up.

### Accessibility tree snapshot ADR

The [accessibility ADR][selenium-18205] adds a method on the driver and on elements that returns an
accessibility tree snapshot. Implementations have already shipped in Python and JavaScript; the
Ruby, Java, and .NET implementations were rolled back so they can be reviewed for idiomatic fit. The
one change [titusfortner] requested, now in the record, is that when the driver is switched into a
frame the snapshot covers that frame, as a screenshot does. [titusfortner] felt the record carries
more implementation detail than an ADR needs, such as whether .NET and Java cast to reach the
method; [AutomatedTester] said that detail came from review feedback.

[diemol] asked how method names and placement for Java and .NET would be agreed, for example top
level or under an accessibility namespace, to avoid delays. [AutomatedTester] has already shared a
plan with the .NET maintainer and will post a plan for each remaining binding before implementing.
[titusfortner] said what the ADR needs is a name that is consistent across bindings, such as
accessibility snapshot rather than a11y tree, not whether an interface is used.

### Low-level event subscription ADR

[titusfortner] wrote the [low-level event subscription ADR][selenium-18299] after reviewing
[AutomatedTester]'s network ADR implementation. The [BiDi implementation boundaries
ADR][selenium-17670] assumes callers can add listeners for event subscriptions at the low level,
but the bindings have not implemented that there, and each binding's existing listener support
behaves differently. The record defines what the low level must support so the high-level API can
build on it, in three parts: listeners, invocation, and failures. An earlier draft tried to do too
much in the low level; [titusfortner] narrowed it after looking at how [jimevans] structured
WebDriverBiDi.NET. For Java, Ruby, and Python, low-level domains get add and remove methods that
take a callable. Listeners stay separate from subscriptions: the subscribe command carries any
scope, while a listener receives every payload for its event and does any filtering in its
callable, which is a high-level concern. [titusfortner] may soften the wording so the .NET async
equivalent conforms, since adopting that pull model in the synchronous bindings would leave thread
handling to callers.

The main open question is whether listeners run sequentially or concurrently. Sequential listeners
let users append to a simple array without threading or deadlock concerns and keep logs in order,
but cost performance, especially remotely. [titusfortner] believes part of the slowdown the .NET
maintainer attributes to intercepting by default comes from handling intercepted requests one at a
time, waiting a full round trip for each continue command, which for a page with 100 requests could
add 20 to 30 seconds. Playwright requires an explicit pattern to intercept everything, while the
network ADR currently intercepts by default. [titusfortner] proposed that the low level support both
modes per listener and leave defaults to the high-level API, for example concurrent for network and
sequential for ordered script logs. [titusfortner] also raised draining queued payloads before a
session ends, and letting a listener remove itself.

[AutomatedTester] argued execution order should be left to each implementation, made as performant
as possible: nothing in the browser is sequential, events can come from different frames and start
firing before a page finishes loading, timestamps are not guaranteed to be in order anyway, and
most users only care that their handler runs. [AutomatedTester] also raised the added latency of a
remote Grid. [jimevans] explained that WebDriverBiDi.NET lets each handler run synchronously or
asynchronously, defaulting to synchronous because most handlers only capture event data, and
requiring asynchronous mode when a handler sends commands, as network interception often does. That
design was driven by the .NET runtime, where the WebSocket handles one message at a time and
awaiting a command response inside a handler can deadlock. [jimevans] left open whether Selenium
should expose that choice to users. [AutomatedTester] took this as a reason not to expose an
execution mode at all; [titusfortner] said the synchronous bindings can manage with basic threads,
and that users will still ask why events arrive out of order. [titusfortner] said the modes could be
dropped if listeners are concurrent, and framed the choice as requiring concurrency, supporting both
at the low level, or leaving it to each binding. [diemol] asked whether Playwright's remote server
processes events server side; [titusfortner] understood its JavaScript still runs locally and that
it is not designed for remote execution, which may give Selenium's native bindings a performance
advantage.

Event payloads do not identify which subscription produced them, so Selenium has to match browsing
contexts itself. [pujagani], recalling a mention by [AutomatedTester], noted the [open specification
issue][webdriver-bidi#1032] on this.
[jimevans] said the specification now requires every event payload to include the browsing context
and user context, though browsers may not have caught up, but does not expect subscription IDs to be
added, since they could expose details unrelated to the session. [jimevans] would keep a local
browsing context tree updated through system-level subscriptions, so frame and window switching
needs no remote calls, and is not persuaded by concerns about missed events, which would indicate a
failure in the local architecture or the remote end. [titusfortner] agreed, and both noted the tree
is outside this record's scope. [titusfortner] said settling this record blocks implementing the
network ADR. [diemol] and [pujagani] want to read it more closely first.

### Release and CI improvements

[diemol] is finishing Docker Selenium work, then will publish the release blog post and run the next
release personally to check that the process works. [titusfortner] found that the EngFlow cache can
be used on the GitHub Actions runners through a settings toggle, making caching work from earlier in
the year unnecessary, which should sharply reduce PR run times. Changing only the version no longer
invalidates the test cache in any binding, so a release that just bumps the version reuses earlier
test results, and releases may get under half an hour. The npm and NuGet problems from the last
release are fixed, with trusted publishing now enabled for NuGet. [titusfortner] believes every
package registry now uses trusted publishing except Java's, where it is not available.

## Meeting Summary

Only two TLC members attended, along with guests including Navin from TestMu AI, so the meeting was
mostly updates and planning. [titusfortner] covered the release automation, the Selenium Manager
cross-compile, and how Python moves to the generated BiDi layer. Most of the remaining discussion
was about what Selenium 5 still needs beyond the merged ADRs, including other BiDi events, possible
subscription and capabilities ADRs, and splitting the [interaction readiness ADR][selenium-17886].

## Decisions

* [titusfortner] proposed keeping Selenium 5 simple by releasing only the synchronous API, with any
  async API built on top of it afterward, and [diemol] agreed this does not need to be solved now.
* [diemol] agreed with [titusfortner] that, now that several ADRs have merged, the next step is to
  identify what else Selenium 5 needs, such as support for other BiDi events and possible
  subscription and capabilities ADRs, before diving into the network implementation.

## Discussion Notes

### Moving the JavaScript bindings to TypeScript

Navin described a plan, discussed with [harsha509], to move the JavaScript bindings to
TypeScript, with TypeScript building the JavaScript files. JavaScript would stay supported for some
time, and starting with Selenium 5 it could be deprecated in favor of TypeScript. [titusfortner]
said the plan made sense.

### Release automation and CI test changes

[titusfortner] spent the week on build and release improvements, since releases will essentially
need to happen every two weeks going forward. CDDL regeneration, dependency updates, and CDP updates
are now outside the release, so the release only builds and publishes. The pre-release PR now
[merges automatically][selenium-18018] once RBE and CI are green, and publishing continues from
there. Asked by [diemol], [titusfortner] said it is the only PR that merges automatically. The last
release took about 90 minutes and the next should take about 50. On [diemol]'s last release, the
only issue was the CDDL needing regeneration for Ruby, which no longer happens in the release.

Python PRs now [run a smaller set of high-value tests][selenium-18040], and Python and Ruby run
longer suites nightly. Before a release, the scheduled nightly runs should be checked for failures.
A weekly flakiness report is also running to find further optimizations.

### Python BiDi transition and web extensions implementations

The merged [BiDi implementation boundaries ADR][selenium-17670] says BiDi domains should not be
exposed directly off the driver; instead the driver gets specific methods, such as installing a web
extension. For Python, the low-level code generated from the specification lives in a private
`_bidi` module that anyone can still import, and the driver-level methods wrap it. Navin said the
existing Python BiDi implementation has users, based on the issues opened, though there is no usage
data. [titusfortner] expects the transition to be messy: some domains can be deprecated as a whole,
with a notice pointing to the replacement and asking users to request any driver wrapper they need,
but features such as network interception have to be reworked onto the new generated code.
[titusfortner] asked whether Navin might be interested in helping sort this out, and suggested
discussing the Python approach once Ruby is in better shape.

[titusfortner] requested changes on [AutomatedTester]'s [Python web extensions PR][selenium-17970]
so it uses the new generated code instead of the old. The new approach pulls in vendor-specific CDDL
files automatically, so the Mozilla namespace is already in the schema and the `_bidi` module
should have classes for it, with nothing browser-specific to add by hand. [diemol] said
[AutomatedTester] had posted that the change was made, and [titusfortner] found the update during
the meeting.

[titusfortner] reviewed [pujagani]'s [Java BiDi generator][selenium-17777] and found a few things
to fix. The [Java web extensions PR][selenium-18036] does not use the schema yet; [titusfortner]
suggested merging the schema with the vendor extensions first and basing the web extension work on
it. Once the Java generator lands, Java, Python, and Ruby will all have generated code that matches
the [low-level BiDi ADR][selenium-17786]. [pujagani] was looking at the same for
[JavaScript][selenium-17973], but its status was not known.

### Selenium Manager binaries

[titusfortner] has set up the [cross-compile][selenium-18029] of Selenium Manager and will step back
from the last part, which [AutomatedTester] may take on. The result is six separate binaries, x64
and ARM64 for each of macOS, Linux, and Windows, and each binding will reference the ones it needs.
[diemol] had expected five; the sixth is Intel macOS, which is still supported. Two things change.
The minimum required Intel macOS version goes up to match the ARM minimum because of how the
cross-compile works, though it is still an old release. And 32-bit Windows is no longer supported,
which turns out to have accidentally been the case for about a year and a half. The project may
still publish debug binaries, and possibly a 32-bit Windows binary, to the artifacts repository.

### Docker Selenium releases

[titusfortner] asked whether [diemol] knows how to release Docker Selenium, since people have been
asking about it in Slack and the process should not depend on one person. [diemol] used to do it and
would need to check; if the structure is unchanged, triggering one GitHub Actions workflow should
release everything, though that was not certain. [diemol], who previously managed the project,
noted the images now bundle much more than they did then, which makes them harder to maintain.
Docker Selenium releases used to go out the same day as Selenium, and it had already been updated
to 4.49, so it may only need a trigger. [titusfortner] has asked in Slack for documentation and
suggested automating the release or starting it alongside the Selenium release.

### Script and logging ADR review

[titusfortner] asked [diemol], as the final sign-off, to prioritize approving the [script and
logging ADR][selenium-17776]. [diemol] has not had time for ADR reviews recently and has been
handling PRs unrelated to Selenium 5 and BiDi so [titusfortner] does not need to. [diemol] listed
the items to look at: the script and logging ADR, the [interaction readiness ADR][selenium-17886],
which [diemol] wants to understand first, a Java logging request a contributor has been asking
about for a while, and one more item that could not be recalled.

### Remaining Selenium 5 scope

[titusfortner] plans to work next on the Ruby implementation of the [network ADR][selenium-17685].
The transport layer and subscription mechanics in the WebSocket class probably do not need an ADR,
but the ADRs so far only cover subscriptions and async events for network, logging, and script.
BiDi has other events users can subscribe to, and Selenium 5 probably needs to support them somehow,
so [titusfortner] wants to first review what can be subscribed to and what every binding needs to
support. Some navigation events tie into user contexts and may tie into the interaction readiness
work. This may need a subscription ADR.

Capabilities may also need an ADR. In WebDriver Classic, capabilities are sent to the remote end,
which manages everything. In BiDi, settings such as timeouts and page load behavior are passed in
individual commands rather than capabilities, so the bindings will have to manage a number of them
locally. Options include driver-level capabilities that could change during a session, or a waiting
strategy argument on every navigation or click. [titusfortner] suggested a broader look at which
capabilities are global and managed remotely and which must be local.

The BiDi specification also changed what unhandled prompt behavior means. In Classic, it covers
what happens when a command unrelated to an open alert runs; in BiDi, it covers what happens when an
alert opens. [titusfortner] has raised the naming in the specification several times without
getting it changed. Either way, the bindings need to handle backward compatibility locally or
remotely, and an ADR could document the behavior every binding needs.

### User contexts and async APIs

[AutomatedTester] has proposed using user contexts so one driver can host multiple independent
sessions, for example getting a new session from a tab instead of a new driver. [titusfortner] sees
that as a completely new API for Selenium that adds little over the current approach of explicitly
moving driver focus between windows and frames, and wants that implemented first. Python could also
use async/await to run work in parallel, which Java and Ruby will not, and Playwright supports both
sync and async APIs. [diemol] did not see why this needs solving now, since users can already create
more user contexts through the low-level API, much as they do in Playwright. [titusfortner] said the
idea is a native Selenium API rather than low-level calls, and that sharing one socket connection
across sessions could improve performance. [diemol] questioned how much a wrapper matters given how
much code is no longer written by hand.

Navin asked what is wrong with manually creating a user context and a browsing context inside it,
and whether the proposal is documented. [titusfortner] explained its two parts: async/await support
for running things in parallel, and multiple sessions over one socket connection, with the goal of
keeping the API from falling behind Playwright. [titusfortner] wants to focus first on what is
known to be needed for Selenium 5 without ruling out later work.

### Interaction readiness ADR

[titusfortner] thinks the [interaction readiness ADR][selenium-17886] combines concerns that should
be separate, and prefers smaller atoms that each take the arguments they need over one atom with
many optional arguments. Settledness needs a ledger of activity, such as the time since the last
network request, while interactability does not. [titusfortner] would preload and pin the ledger,
then have one atom that queries it to determine settledness and a separate atom built into element
methods such as click, send keys, and clear to wait for interactability. That wait has to stay
compatible with users' current explicit wait strategies while allowing more flexibility for async
use, possibly with events users can act on. [AutomatedTester] revised the ADR after earlier
feedback, but [titusfortner] has not yet reviewed the updates or followed up with revised ideas, and
is setting it aside for now to focus on BiDi.
